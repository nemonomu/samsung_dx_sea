# BestBuy 수집 복구와 판정

운영 fullrun의 `browser_graphql` 목록·상세 경로에 적용합니다. 기존 비브라우저 경로와 수동 canary 진단은 유지합니다. DB 스키마와 기존 환경변수 이름은 변경하지 않습니다.

## 목록

- 요청 오류와 정상적인 빈 목록을 구분합니다. HTTP 200만으로 성공 처리하지 않습니다.
- 응답의 일반 상품·광고 상품 SKU와 파싱한 순서를 대조합니다. 정상 combo 문서는 기존 정책대로 제외하며 그 원래 위치는 보존합니다.
- 한 페이지가 실패하면 다음 페이지로 넘어가지 않습니다. 대기 후 그 페이지로 복구를 확인하고, 복구되면 해당 목록의 1페이지부터 다시 수집합니다.
- 복구 확인 간격은 30초, 120초, 300초, 600초입니다. 복구돼도 간격 단계는 초기화하지 않습니다. 브라우저 재시작은 한 번으로 제한합니다.
- 전체 목록 시도는 최초 포함 3회, 첫 실패 이후 복구·재수집은 30분 한도입니다. 진행 중 요청은 설정된 전송 타임아웃에 따라 종료되며, 기한 뒤 도착한 결과는 채택하지 않습니다.
- 페이지 간 일반 상품 중복은 목록이 바뀌었을 가능성으로 처리해 그 시도를 폐기합니다. 다른 시도의 페이지를 섞지 않습니다.
- 서버의 고정 스냅샷이 아니므로 전체 목록이 동일 순간의 순위임을 보장하지 않습니다. 시도·페이지별 시각과 SKU 순서를 남깁니다.
- 검증된 목록의 CSV와 manifest 저장이 끝나야 `collection_status.json`을 `complete`로 바꿉니다.

## 상세

- 실제 상세·리뷰·비교상품 요청 결과로 항목별 성공을 판정합니다. 첫 상품의 비교상품 오류가 전체 상세수집의 사전 점검 실패가 되지 않습니다.
- 정상 결과 없음(`empty`), 성공(`success`), 불필요(`not_required`), 실패(`failed`), 미실행(`pending`)을 구분합니다.
- 기존 API 요청과 최종 컬럼은 유지합니다. 비교상품 응답의 `productBySkuId.reviewInfo` 또는 추천 상품 `item.reviewInfo` 아래 `proFeatures`·`conFeatures`에 발생한 `NOT_FOUND`만 부가 경고로 구분합니다. 요청 SKU와 목록 구조, 추천 상품 SKU·상품명을 검증한 뒤 성공으로 저장하며, 다른 오류나 필수 데이터 누락은 계속 실패 처리합니다. 명시적인 빈 목록과 `null` 목록은 구분합니다.
- 성공에 동반된 부가 오류의 코드·경로·메시지는 상태 파일의 `warnings`, 요청 증거, 항목별 이벤트와 메타데이터에 보존합니다. 이 성공 결과는 다른 상품의 재시도나 같은 실행의 재개 때문에 다시 요청하지 않습니다.
- 상품별 오류는 최초 포함 최대 3회 시도합니다. 성공한 항목은 보존하며 실패 항목만 요청합니다. 영구적인 쿼리 오류는 반복하지 않습니다.
- 전송 장애는 전체 요청을 잠시 멈추고 동일한 공유 시간·대기 예산으로 복구합니다. 복구가 소진되면 뒤쪽 상품은 `pending`으로 남깁니다.
- SKU와 확정된 순위는 삭제하거나 당겨 매기지 않습니다. 실제 실패 항목은 JSON에서 `null`, CSV에서는 빈 셀로 표현하며 상태 파일로 원인을 구별합니다. 관측된 유효한 목록 값은 보존합니다.
- 같은 날·같은 대상 목록의 재개는 검증된 성공 기록과 파일을 확인해 재사용합니다. 날짜가 바뀐 실행은 새 수집 폴더에서 목록부터 시작해야 합니다.
- 미완료 결과는 `output/partial_output.csv`, `output/partial_output.json`에 저장합니다. 기존 `final_output.csv`를 실패 결과로 덮어쓰지 않습니다.
- 필수 항목 미완료 상태에서는 최종 CSV 확정, S3 업로드 및 DB 반영을 막습니다. 남은 실패와 대기 항목을 모두 알립니다.

## 진단 자료와 메일

- 목록 상태: `<run>/main/collection_status.json`, `<run>/bsr/collection_status.json`
- 상세 상태: `<run>/output/collection_status.json`
- 시도별 증거: 해당 단계의 `recovery/<invocation>/events.jsonl`과 요청·응답 JSON
- 상세 미완료 목록: `<run>/detail/parsed/detail_failures.csv`
- 기존 상태는 새 invocation의 `previous_status.json`에 보존합니다. 각 요청은 고유 증거 경로를 사용합니다.
- 로그는 코드 커밋, 주요 설정, 요청 식별값, SKU·페이지·순위, 세션 세대, 대기·재시작, 오류 경로, 최종 채택 시도를 기록합니다. 원인에 대한 추정과 성공 판정을 섞지 않습니다.
- 인증 키·쿠키·토큰·이메일 등의 민감 필드는 진단 증거에서 가립니다.
- 기존 fullrun의 알림 경로에서 정상/부분 완료/미완료를 구분하고, 단계별 건수·미완료 SKU와 순위·실패 항목·요청 횟수·종료 사유·반영 보류를 읽기 쉬운 형태로 보냅니다.
- 성공한 항목의 장단점 요약 오류는 진단 기록에만 남기고 메일에는 표시하지 않습니다. 미완료 목록의 실제 요청 횟수와 응답 판정 횟수는 별도로 표시하며, 실패 CSV에도 두 횟수를 기록합니다.
- 이 변경은 AI 서비스를 자동 호출하지 않습니다. 저장된 구조화 증거를 AI 또는 사람이 비교·분석할 수 있게 합니다.

## 오프라인 검증

`tests/test_collection_recovery.py`는 네트워크 모의 응답과 가상 시계를 사용합니다. 페이지 누락, 목록 재시작, 회복 후 재실패, 시간 초과, 비교상품 부분 실패, 재개, 잘못된 SKU, 오래된 캐시, 메일 요약과 후속 단계 차단을 검증합니다. 실제 사이트·DB·S3·메일 발송 검증과 구분합니다.
